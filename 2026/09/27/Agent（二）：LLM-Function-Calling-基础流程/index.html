Agent（二）：LLM Function Calling 基础流程

发表于2026-09-27|更新于2026-09-28|Agent-从0到1
|浏览量:

来自 llm_function_call.ipynb：大模型工具调用（Tool / Function Calling）的基础闭环。

核心流程：用户提问 → 模型决定调用哪个函数（返回 tool_call）→ 本地执行函数 → 把结果回传 → 模型生成最终回答。

核心组件

组件 说明
tools 向模型注册的函数 Schema（名称、描述、参数）
get_weather() 本地实际执行的 Mock 天气查询函数
send_messages() 封装 API 调用，传入 messages_history + tools
messages_history 多轮对话历史，贯穿整个调用链

1. 客户端与工具函数

hasattr 的鸭子类型判断

hasattr(msg, "model_dump") 检测的是 msg 对象上有没有 model_dump 这个属性/方法，语义是「试着访问 obj.name，能访问到返回 True，抛 AttributeError 返回 False」——会查遍自身属性、类属性、父类方法。

它解决的实际问题：messages 列表里混着两种东西——

  1. 自己写的 dict：{"role": "user", "content": "hi"}
  2. 上一轮 API 返回的 message 对象（多轮对话时把 assistant 回复塞回历史）

API 只吃 dict，不吃对象。这个函数像一个「适配器」：是对象就转 dict，本来就是 dict 就直接过。

为什么用 hasattr 而不是 isinstance：isinstance 要求导入并绑定具体类（openai.types.chat.ChatCompletionMessage），SDK 升级改了类路径代码就碎。hasattr 只依赖「有没有这个方法」这个行为特征，更宽松、更抗变化——「看起来像鸭子、叫起来像鸭子，那就当它是鸭子」。代价是理论上可能误判，但 model_dump 基本是 Pydantic 的招牌，实际碰撞概率可忽略。

2. 注册工具：函数 + Schema

tools 是 JSON Schema 形式的函数说明书：告诉模型「我这有 get_weather 可用，参数长这样」——相当于递给服务员一份菜单。

3. 第一轮调用：模型「点单」

返回的 message 里 content 是空的，tool_calls 里装的是一张点单：

我想调 get_weather，参数是 {"location": "Hangzhou, Zhejiang"}

——菜还没做。模型并不会自己执行函数，真正执行 get_weather() 的是本地代码。

4. 关键机制：无状态 + 成对消息

1. API 是无状态的。 第 1 次调用结束后，服务器不记得刚才发生过什么。发起第 2 次调用时如果只发 [user]，模型面对的就像一个全新对话——它不知道自己点过单，更不知道天气结果。所以必须把完整的来龙去脉重新发一遍。

2. 协议要求成对出现。 OpenAI 风格的 API 硬性规定：role: "tool" 的结果消息，前面必须紧跟一条带 tool_calls 的 assistant 消息，且 tool_call_id 要对得上，缺了直接报 400。所以顺序是：
