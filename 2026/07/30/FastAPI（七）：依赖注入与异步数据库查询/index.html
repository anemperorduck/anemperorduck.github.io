FastAPI（七）：依赖注入与异步数据库查询

async_sessionmaker：生产会话的工厂

AsyncSessionLocal 这个名字是我自己取的，它本质上是一个“会话工厂”，但还不是会话本身。

async_sessionmaker 会根据传入的参数配置好一条“生产线”，每次调用 AsyncSessionLocal() 都会产出一个新的 AsyncSession 对象。理解这一点很重要，因为后续依赖项里用 async with AsyncSessionLocal() as session 拿到的 session 就是一个全新的会话，每个请求之间互不干扰。

关于几个常用参数：

  • bind：绑定到之前创建好的异步引擎，会话会从引擎维护的连接池里取连接。
  • class_：指定会话类，异步场景固定使用 AsyncSession。
  • expire_on_commit=False：这个参数在异步开发里建议设为 False。如果保持默认的 True，提交事务后所有已加载的对象会被标记为“过期”，下次访问对象的任意属性时会隐式地向数据库再发一次查询。在异步代码里这种隐式 IO 很容易踩坑，关掉之后对象提交后仍然可用，行为更可控。

AsyncSession：通往数据库的“电话线”

路由函数里的 db 参数就是 AsyncSession 的实例，它是和数据库交互的核心对象。除了直接执行 SQL，它还负责追踪 ORM 对象的状态、管理事务。

在今天的查询接口里我们用到了 db.execute()，但会话的职责远不止这一个。这里列几个最常用的方法，心里有个印象就行，后面实践多了自然会记住：

  • db.add(obj) — 把新对象标记为待插入
  • await db.commit() — 提交当前事务
  • await db.rollback() — 回滚
  • await db.flush() — 把未提交的改动刷到数据库，但不提交事务
  • await db.refresh(obj) — 从数据库重新加载一个对象的最新状态
  • await db.get(Model, pk) — 按主键查询

一个容易被忽略的点是，会话内部有一级缓存（Identity Map）。同一个主键的对象在同一会话内如果被查询两次，第二次不会真的访问数据库，而是直接从缓存中返回。这个特性在循环查询或者更新场景下要心里有数，否则可能“改完再查出来的还是旧的”，因为查的是缓存，不是库里的最新值。

execute() 与 Result：数据什么时候到内存

查询路由里这段代码涉及两个步骤：

await db.execute(select(Book)) 执行之后，SQL 语句已经发送给数据库并执行完毕了，但数据还在数据库的游标里，没有拉到 Python 内存中。result 是一个 Result 对象，它封装了这次查询的结果集。

接下来的 .scalars() 会返回一个 ScalarResult，它仍然是一个可迭代对象，数据还是懒加载的。直到调用 .all() 时，才真正从游标中把所有行拉取到内存，封装成一个 Python 列表。

之所以用 .scalars()，是因为 select(Book) 查询出来的每一行都是一个 Row 对象，而这个 Row 里只有一个元素——完整的 Book ORM 实例。scalars() 的作用就是去掉外面的 Row 包装，直接取第一列的值，所以我们最终拿到的是 list[Book]。

如果是聚合查询，比如 select(func.count()).select_from(Book)，结果就只有单个标量值，这时候用 result.scalar() 拿到的直接就是那个数字，不需要再 .all()。

注意

1. expire_on_commit 和异步场景的匹配

默认情况下 SQLAlchemy 在提交事务后会让所有对象过期，下次访问属性时自动重新查询。这在同步代码里问题不大，但在异步环境里，如果提交后你还在用这个对象（比如在返回之前读它的某个属性），就会触发一次隐式的 await 查询，而且你还意识不到。直接把 expire_on_commit 设为 False 可以避免这类隐式异步 IO，让对象的行为更可预期。

2. 不要把 ORM 对象直接当作 API 返回值

这一节为了演示查询流程才直接返回 Book 对象列表。实际项目里一旦表结构稍微复杂一些，加上关联关系和敏感字段，这种做法很快就会失控。尽早引入 Pydantic 模型作为响应 schema，既是给前端一份稳定的契约，也让后端的序列化逻辑变得可控。这个会在后续的笔记里专门展开。
