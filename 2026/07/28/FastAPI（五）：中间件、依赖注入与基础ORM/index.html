FastAPI（五）：中间件、依赖注入与基础ORM

发表于2026-07-28|更新于2026-07-28|世界模式
|浏览量:

这一节记录我在学习 FastAPI 进阶特性时的一些整理。中间件、依赖注入和异步 ORM 看似独立，但在实际项目中往往会同时出现，一旦把它们串起来理解，很多之前觉得别扭的代码会突然变得清晰。

下面我会先梳理这三个概念各自的原理和定位，然后用一个完整的示例把它们组合起来，最后给出运行方式以及两个生产环境里容易被忽略的问题。

核心概念梳理

中间件

中间件是位于 HTTP 请求和路由处理器之间的一层逻辑。每一个到达服务器的请求，在进入具体的路由函数之前，都会先穿过所有中间件；路由处理完毕后，响应再按照相反方向穿过这些中间件，最后返回给客户端。

FastAPI 中通过 @app.middleware("http") 注册的中间件，本质上是一个异步函数，接收 request 和 call_next 两个参数。call_next 负责把请求传递到下一个中间件或最终路由，并返回响应。你可以在调用它之前做一些事情（比如记录开始时间、生成追踪 ID），也可以拿到响应之后再做一些事情（比如写入耗时信息、添加安全头部）。

这种“前置 - 传递 - 后置”的结构，让中间件非常适合处理日志、性能监控、CORS、全局异常兜底这类跟业务逻辑无关但又必须存在的横切关注点。

依赖注入

FastAPI 的依赖注入基于 Depends 关键字，它的核心思想是“控制反转”：路由函数不再自己创建或管理外部资源，而是声明“我需要什么”，由框架负责提供。

最常见的应用场景有两个：一是资源生命周期管理，比如数据库连接。一个依赖函数里用 yield 抛出 Session，路由使用完毕之后，框架会自动执行 yield 后面的提交或关闭代码，开发人员不必在每个路由里重复写 commit 和 close。二是服务组装，比如注入 AI 客户端、配置对象等，这样测试时可以很方便地替换实现。

yield 在依赖注入中的工作机制值得单独说一下。FastAPI 内部会把依赖生成器推进到 yield 处，取出抛出的值注入路由；路由执行完毕后（无论成功还是异常），框架会继续推进这个生成器，执行 yield 后面的清理逻辑。这个过程的实现不需要多线程或信号量，完全依靠 Python 生成器的协程特性，所以性能损耗很低。

异步 ORM

在异步 Web 框架里使用 ORM，最大的一个区别是要采用异步驱动。比如 SQLAlchemy 默认是同步模式，如果直接把同步版的会话放进 FastAPI 的 async def 路由里，它会阻塞事件循环，导致整个服务的并发能力下降。

解决方式就是换上异步引擎：使用 create_async_engine 搭配 aiosqlite 或 asyncpg 等异步驱动，再通过 async_sessionmaker 创建异步会话工厂。这样数据库操作就能以非阻塞的方式进行，与 FastAPI 的协程模型保持一致。

另外，异步环境下要格外注意 ORM 的惰性加载行为。同步时自动触发的隐式查询在异步环境里会直接抛异常，所以一般建议在定义模型关系时采用 lazy="raise"，并在查询时显式使用 selectinload 等手段预先加载所需数据。

1. 数据库引擎、会话工厂与 ORM 模型

create_async_engine 会维护一个连接池，不是立即连接数据库。async_sessionmaker 像是工厂，每次调用都产生一个新的 AsyncSession，互不影响。

关闭 autocommit 和 autoflush 是为了精确控制事务边界。expire_on_commit=False 则让提交后的对象属性依然可访问，不会因为后续访问而发出隐式查询。

ChatHistoryModel 就是一张聊天记录表。created_at 使用带时区的 datetime.now(timezone.utc) 再剥离时区信息，替代了已被弃用的 utcnow；lambda 保证每条记录插入时都是当前时间。

2. 请求/响应模型与模拟 AI 代理

MockLangChainAgent 只暴露一个 ainvoke 异步方法，和 LangChain 中 Runnable 的接口保持一致。以后替换为真实的 LLM 链，依赖注入层和路由代码都不需要动。

3. 依赖注入函数

get_db 用 yield 托管 Session 的生命周期。路由正常返回，yield 之后的 commit() 会把数据真正写入数据库；如果路由抛出异常，rollback() 会撤销所有未提交的改动。finally 里的 close() 确保连接一定会归还连接池，这是最容易被忽略却最关键的一环。

get_ai_agent 看起来简单，但它完成了服务实例的创建解耦。测试时如果需要替换为假实现，只需要修改这一个地方。

4. 自定义中间件与应用实例

request.state 是 ASGI 规范里预留的容器，用来在中间件和路由之间传递数据，trace_id 放进去后，后续任何依赖或路由都可以直接取用。

异常捕获那一层避免了中间件因为下游未处理异常而自身崩溃，保证至少返回一个结构化的 500 响应。

5. 路由处理器

路由只保留业务步骤：调用 AI、拼装记录、登记到会话、返回结果。事务提交和连接关闭全交给依赖注入层。

db.add(chat_record) 只是把对象注册到工作单元，并没有真正写入数据库。这个写入动作会推迟到 get_db() 的 commit() 执行。

两个生产环境里容易被忽视的地方

中间件与流式响应

@app.middleware("http") 背后是 Starlette 的 BaseHTTPMiddleware，它很方便，但对流式响应不太友好。如果在中间件里 await response.body()，整个响应流会被消费掉，导致客户端收不到数据。LLM 应用里经常需要流式输出，碰到这种情况，可以考虑用纯 ASGI 中间件，或者确保中间件完全不碰响应体。

异步 ORM 下的惰性加载

SQLAlchemy 默认的关系加载方式是惰性的。在同步代码中，你在循环里访问一个未加载的属性，它会静默发 SQL 补上。但在异步环境里，这种做法会抛出 MissingGreenlet 异常。解决办法是定义模型关系时设置 lazy="raise"，让潜在问题尽早暴露；查询时用 selectinload 或 joinedload 显式预加载，避免隐式查询的发生。
